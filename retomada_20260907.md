## Scheduling Service concluído

- Clean Architecture organizada.
- Criação, listagem, consulta por ID e atualização de agendamentos.
- `createdAt` e `updatedAt` persistidos.
- UUID gerado pelo JPA na criação; o domínio usa `id = null` para novos registros.
- Horários normalizados para precisão de minuto.
- Conflito de agenda por médico:
  - intervalos menores que 30 minutos são rejeitados;
  - exatamente 30 minutos é permitido;
  - o próximo horário disponível é retornado em `suggestedAppointmentDate`.
- Validação aplicada tanto no POST quanto no PUT.
- Migrations Flyway aplicadas até a V4:
  - V1: tabela de agendamentos;
  - V2: `updated_at` obrigatório;
  - V3: índice de proteção de horário;
  - V4: constraint PostgreSQL de sobreposição de agenda.
- Eventos RabbitMQ publicados depois do save:
  - `AppointmentCreatedEvent`;
  - `AppointmentUpdatedEvent`.
- Filas separadas:
  - `hospital.appointments.created`;
  - `hospital.appointments.updated`.
- Exchange: `hospital.appointments`.
- Routing keys:
  - `appointment.created`;
  - `appointment.updated`.
- O scheduling-service é produtor. O consumo ficará no futuro `notification-service`.
- O consumidor futuro deverá usar ACK manual, retry e idempotência para evitar problemas de ordem entre criação e atualização.
- Logs com SLF4J e Loki4j enviados ao Loki/Grafana.
- Query inicial no Grafana:

```logql
{app="hospital-scheduling-service"}
```

- Para procurar mensagens de persistência:

```logql
{app="hospital-scheduling-service"} |= "Persistindo agendamento"
```

## Segurança Keycloak concluída

- Realm único: `hospital`.
- Client: `hospital-api`.
- Roles:
  - `DOCTOR`;
  - `NURSE`;
  - `PATIENT`.
- Usuários de avaliação:
  - `doctor.test / Hospital@123`;
  - `nurse.test / Hospital@123`;
  - `patient.test / Hospital@123`.
- Keycloak importado automaticamente pelo Docker Compose através de:
  - `keycloak/realm-hospital.json`;
  - comando `start-dev --import-realm`.
- Hostname atual para acesso da banca:
  - `192.168.137.2`.
- Issuer usado pelo scheduling-service:

```text
http://192.168.137.2:8080/realms/hospital
```

- Token JWT validado pelo Spring Security Resource Server.
- Sem token, a API retorna `401`.
- `DOCTOR` e `NURSE` podem criar e atualizar.
- `PATIENT` pode apenas consultar via GET.
- O scheduling-service lê `patientId` do JWT para filtrar os agendamentos do paciente.
- A claim esperada no JWT é:

```json
{
  "patientId": "id-do-paciente",
  "realm_access": {
    "roles": ["PATIENT"]
  }
}
```

## Próximo trabalho: patient-service

Objetivo: ao criar um paciente, gerar o `patientId` no `patient-service` e criar/vincular o usuário no Keycloak.

Fluxo planejado:

```text
POST /patients
  -> patient-service gera patientId
  -> salva dados do paciente
  -> cria ou atualiza usuário no Keycloak
  -> atribui role PATIENT
  -> grava patientId como atributo do usuário
  -> Protocol Mapper inclui patientId no access token
```

O `patient-service` não deve armazenar senhas. O Keycloak será responsável por identidade, senha, autenticação e roles. Os dados clínicos permanecem no banco do `patient-service`.
